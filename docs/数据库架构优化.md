# 本地历史库（history.db）架构与查询性能优化

> 2026-11-05 · 改造对象：`justoneapi_collector/history_store.py`
> 一句话：把「每天一行的明细表」当成「每作品一行的看板表」用，是这次所有卡顿的根因。
> 拆成**事实表 + 派生表**之后，看板首屏从 4.2 秒降到 1 毫秒以内，而且随数据增长不再恶化。

---

## 一、改造前的实测数字

体检对象：真实用户库（`%APPDATA%\TrafficCatcher\history.db`）当时只有 19 行、52KB。
**所以「现在不卡」是假象** —— 真正的形状要放大到真实使用量才能看见。

因此用等价 schema 造了三个规模的库来量：

| 规模 | top_posts | author_posts | tracked_authors | stats（卡片） |
|---|---|---|---|---|
| 19 行（真实库现状） | 0.10ms | 0.01ms | — | 0.02ms |
| 27 万行 | 20ms | 23ms | — | 47ms（5 条查询合计） |
| 90 万行 | 329ms | 417ms | 85ms | 135ms |
| **106 万行（5 万作品 × 100 天）** | **4151ms** | **3969ms** | **3726ms** | **350ms** |

最后一行是关键：一样是「100 万行」，作品池大（5 万件）比作品池小（4 千件）慢 12 倍。
因为查询要按 `(platform, post_id)` 分组 —— **分组数才是成本，行数只是表象**。
用户用得越久、挖的号越多，这个数字只会更差。一次看板刷新 4 秒，等于软件假死。

---

## 二、根因（四条，按影响排序）

### 1. 用错了表 —— 明细表被当快照表查（影响最大）

`post_snap` 是「每天一行」的时间序列，天然是 `O(天数 × 作品数)`。
但看板要的是「每作品一行」，于是每次刷新都现算：

```sql
-- 改造前 top_posts
SELECT ..., MAX(day), COUNT(*)
  FROM post_snap WHERE day>=?          -- 扫全部历史
 GROUP BY platform, post_id            -- 5 万组 → 临时 B-tree
 ORDER BY digg DESC LIMIT 200          -- 200 万行的排序，必然落盘
```

`EXPLAIN QUERY PLAN` 显示 `SCAN` + `USE TEMP B-TREE FOR ORDER BY`：
全表扫 + 全量排序 + 落盘，然后才取前 200 条。**为了 200 行，扫了 100 万行。**

### 2. 索引方向不对

- 原来只有 `(platform, author_id)`，而 `author_posts` 还要 `GROUP BY post_id ORDER BY digg`，
  拿不到有序性，只能再排一次；
- `top_posts` 按 `digg` 排序，全库没有任何 `digg` 索引；
- `MIN(day)` / `MAX(day)` 写在同一条 `SELECT` 里，SQLite 会放弃「索引两端」优化，
  退化成全表扫描 —— 这一个细节值 68ms（见第四节）。

### 3. 每次切页都重算统计

`stats()` 是 5 条独立查询，其中 `COUNT(DISTINCT day)` 和 `COUNT(*)` 都是 `O(n)`。
而它只在页面顶部显示四个数字，却被放在 `refresh()` 的最前面同步执行。

### 4. 写入用 `INSERT OR REPLACE`

SQLite 的 `REPLACE` 是「先 DELETE 再 INSERT」：主键索引 + 两条二级索引全部删一遍再插一遍。
同一天反复抓同一批作品，就在库里持续制造半空页 —— 老库越用越慢的隐形原因之一。

## 三、改造方案

### 3.1 事实表 + 派生表（核心）

```
post_snap      事实表   一天一行，只追加          画曲线用（post_trend / author_trend）
author_snap    事实表   一天一行，只追加
     │
     │ 同一个事务内 UPSERT 增量维护
     ▼
post_latest    派生表   一个作品一行            看板用（top_posts / author_posts）
author_latest  派生表   一个账号一行            清单用（tracked_authors）
```

- 派生表是**缓存，不是真相来源**：任何时候都能用 `rebuild_derived()` 从事实表重建，
  所以「派生表算错了」永远有解；
- 事实表一行没动 —— 迁移前后 `post_snap` 的内容哈希完全一致（已实测）；
- 派生表与事实表**在同一个写事务里**更新，不会出现「曲线新、看板旧」。

读路径因此变成按索引取一批行，不再有分组和排序：

```sql
-- 改造后 top_posts
SELECT ... FROM post_latest
 WHERE last_day>=? ORDER BY digg DESC LIMIT 200
-- 计划：SCAN post_latest USING INDEX idx_latest_digg（取够 200 条就停）
```

### 3.2 索引

| 索引 | 服务的查询 | 说明 |
|---|---|---|
| `idx_post_auth_day (platform, author_id, day, author_fans)` | `author_trend` 的粗估源 | 覆盖索引，免回表；替换原来的 `(platform, author_id)` |
| `idx_latest_digg (digg DESC)` | `top_posts` 默认排序 | 逆序索引，取前 N 条即停 |
| `idx_latest_auth (platform, author_id, digg DESC)` | `author_posts` | 过滤完直接有序，零排序 |
| `idx_authlatest_fans (fans DESC)` | `tracked_authors` | 清单天然按粉丝降序 |
| `idx_authlatest_day / idx_latest_last` | 范围过滤 | — |

### 3.3 连接与 PRAGMA

- **每线程一条连接**（原来全局一条 + 一把大锁）：WAL 下读写互不阻塞，
  采集在后台写库时，界面刷不再排队等锁；
- `temp_store=MEMORY`：杜绝临时 B-tree 落盘；
- `cache_size=16MB`、`mmap_size=256MB`、`synchronous=NORMAL`、`busy_timeout=8s`；
- 每条 PRAGMA **单独 try**：某些精简版 SQLite 编译时关了 mmap，不能让一整块异常把后面的设置全带走。

### 3.4 写入

- `INSERT OR REPLACE` → `INSERT ... ON CONFLICT DO UPDATE`（原地更新，不删不插）；
- 事实表 + 两张派生表 + 计数器，**同一个事务**一次提交；
- 补历史数据（day 比库里旧）时，列不覆盖但观察天数照涨 —— 两件事分开用 `CASE` 处理。

### 3.5 计数物化

`_meta` 表存 `rows`（快照行数）和 `days`（记录天数），写入时增量累加，
`prune` / `clear_all` 后重算。看板拿这四个数字从「扫 100 万行」变成「读两行」。

### 3.6 清理不再卡界面

原来 `prune()` 无条件 `VACUUM`：140MB 的库要独占锁 1~3 秒，用户感觉是「点完清理软件卡死了」。
现在只有空闲页占比 ≥25% 才 `VACUUM`，否则 `PRAGMA optimize` 就收工。

## 四、改造后的数字

同一台机器、同一个 106 万行库（5 万作品 × 100 天）、同一批查询：

| 查询 | ①改造前 | ②只换索引 | ③新架构 | ①→③ |
|---|---|---|---|---|
| `top_posts`（爆款库 200 条） | 4151.6ms | 4103.5ms | **0.85ms** | **4902×** |
| `author_posts`（某号作品） | 3969.3ms | 0.3ms | **0.09ms** | **45055×** |
| `tracked_authors`（账号清单） | 3725.7ms | 1305.7ms | **10.66ms** | **350×** |
| `stats`（顶部四张卡） | 350.3ms | 368.1ms | **0.09ms** | **3825×** |
| `post_trend`（单条曲线） | 0.4ms | 0.4ms | 0.4ms | 持平 |

第 ② 列很值得看：**光换索引救不了 `top_posts`**（4103ms，几乎没动）。
索引只能帮「定位」，帮不了「减少要处理的行数」—— 后者必须靠派生表。
而 `author_posts` 在 ② 就够了（单作者的作品很少），说明不是所有查询都需要派生表，
这次改造的收益集中在「全站聚合」这一类。

代价在写入侧：

| 批量 | 场景 | 改造前（仅事实表） | 改造后（事实 + 派生） | 开销 |
|---|---|---|---|---|
| 50 条 | 新的一天 | 0.7ms | 3.4ms | 5.1× |
| 500 条 | 新的一天 | 5.8ms | 21.0ms | 3.6× |
| 2000 条 | 新的一天 | 18.2ms | 77.7ms | 4.3× |

**判断**：真实采集一次 20~50 条，落库多花 2~3ms，而一次网络请求是 200~2000ms，
这点开销在噪声里；换来读路径 3 个数量级的提升，这笔账是划算的。

## 五、兼容性与迁移

| 项目 | 状态 |
|---|---|
| 对外接口签名 | **完全未变**（`stats` / `top_posts` / `author_posts` / `tracked_authors` / `author_trend` / `post_trend` / `snap_*` / `prune` / `clear_all` / `export_rows`） |
| 返回字段 | **逐字段一致**（见第六节等价性校验） |
| 老库升级 | 首次连接自动建派生表 + 回填，`PRAGMA user_version` 记版本，只跑一次。106 万行库实测 3.8 秒，真实用户库（19 行）2.5ms |
| 事实表数据 | **零改动**（迁移前后内容哈希一致） |
| 库损坏 / 缺 sqlite3 | 仍然全部静默降级，不影响采集（自检第 7 节覆盖） |
| 回滚 | 删掉 `history_store.py`，恢复 `history_store.py.bak_20261105_2317` 即可；新增的表和索引对老代码无害（老代码只读 `post_snap` / `author_snap`） |

### 一处有意的语义变化

`tracked_authors()` 返回的 `last_day`：
- 旧：有主页记录时取「作者表的最后一天」，只在作品表出现的号取「作品表的最后一天」；
- 新：统一为「任一来源的最后一天」。

界面不显示这个字段，它只用于 `days=` 的范围过滤，而两种口径在过滤上等价。
改它是为了消除旧实现里同名字段两种含义的隐患。

## 六、怎么验证

三个脚本都是可复跑的，随时可以重放：

```bash
# 1) 契约自检（66 项：每日粒度 / 两来源合并 / 容错 / 并发 / 界面契约）
python tools/_validate_history_store.py

# 2) 行为等价性：同一份数据，旧实现 vs 新实现逐字段比对
python tools/_verify_history_equiv.py

# 3) 性能基准（需先建 264MB 临时库，首次约 50 秒）
python tools/_bench_history_read.py
python tools/_bench_history_write.py
```

本次结果：
- 自检 **66 / 66 通过**
- 等价性：12 个接口 + 3 个「重建后复查」**全部逐字段一致**
- 性能：见第四节

其中等价性校验抓到过一个真实回归，值得记下来 ——
改造初版把账号粉丝数写成「谁新用谁」，于是「今天挖作品顺带抓到 10905」
会把「前天主页上的精确值 58005」顶掉，用户看到的是粉丝暴跌 4 万。
正确规则是**精度优先、其次日期新**，这条现在写在 `_UPSERT_AUTHOR_LATEST` 的注释里。

## 七、还没做的（以及为什么）

| 想法 | 为什么没做 |
|---|---|
| 把 `stats` 的 `posts`/`authors` 也物化 | 派生表只有「作品数」「账号数」那么多行，`COUNT(*)` 已经是 0.01ms，物化反而多一处一致性风险 |
| 写入合并成单条多行 `INSERT` | SQLite 单语句最多 999 个参数，17 列意味着 58 行一句，语句数反而变多 |
| 上 FTS5 做标题搜索 | 目前没有「按标题搜历史作品」的需求；真要做，`post_latest` 上加外部内容表即可，不影响现有结构 |
| 把 `prune` 的 VACUUM 放后台线程 | 现方案（空闲页 ≥25% 才整理）已解决卡顿，后台 VACUUM 会和写事务抢独占锁，收益不抵风险 |
| `snap_days` 按范围重算 | 现在定义是「累计观察天数」，prune 不回退。回退会让老作品的记录天数凭空变少，更容易误导 |
